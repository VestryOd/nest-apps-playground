## Шаг 0 — Скаффолд

Сделано: Nest-приложение, `docker-compose.yml` (Postgres 16 + Redis 7 в Docker), `DatabaseModule` (глобальный, пул `pg.Pool` через токен `PG_POOL`), `RedisModule` (глобальный, `ioredis` через токен `REDIS_CLIENT`), `ConfigModule` на `.env`/`.env.test`, скрипт `npm run migrate` (таблица `schema_migrations`, применяет `.sql` по порядку в транзакции), эндпоинт `GET /health` (проверяет обе базы), `.gitignore`.

Ключевые решения и отступления от исходного плана:
- **Nest 11, не Nest 12.** Nest 12 — чистый ESM (`"type": "module"` в его package.json), из-за этого Jest в CommonJS-режиме не может его `require()` (`SyntaxError: Unexpected token 'export'`). Nest 11 — последний мажор с CJS-сборкой. Договаривались просто на «CommonJS + Jest», но по факту это означало откат на мажор ниже последнего.
- `incremental: true` в `tsconfig.json` убран — конфликтовал с `deleteOutDir: true` у nest-cli (инкрементальный кэш TypeScript считал, что эмитить нечего, даже когда `dist` был физически удалён).
- Тестовая база `nest_apps_test` создаётся автоматически через init-скрипт Postgres в docker-compose (`docker/postgres/init-test-db.sh`).
- `npm audit` показывает 4 high severity в `multer` (транзитивная зависимость `@nestjs/platform-express`, DoS через file upload) — не критично, файлы не загружаем, осознанно не фиксили (потребовало бы отката обратно на Nest 12).
- В песочнице Claude Code переменная окружения `PORT=0` — при ручной проверке через `curl` нужно явно передавать `PORT=3000 npm run start:dev`, иначе Node слушает случайный порт.

## Шаг 1 — Схема БД в миграциях

Сделано: `migrations/0001..0005` — таблицы `users`, `refresh_tokens`, `apps`, `app_versions`, `installs`; `migrations/0006` — переименование `replace_by_token_id → replaced_by_token_id` (написана пользователем как урок «не редактируй уже применённую миграцию, добавляй новую»).

Ключевые решения:
- Внешние ключи — всегда `BIGINT`, никогда `BIGSERIAL` (частая ошибка в черновике: `BIGSERIAL` на колонке FK создаёт свою независимую последовательность вместо того, чтобы просто типизировать колонку).
- Деньги (`users.balance`, `apps.price`, `installs.paid_amount`) — единообразно `NUMERIC(10, 2)`, не `INTEGER` и не `FLOAT`. Уточнение по ходу: `NUMERIC(p, s)` — точный десятичный тип, поддерживает дробные суммы (19.99) без ошибок плавающей точки; это стандартный выбор для денег, не компромиссный.
- Циклическая зависимость `apps.current_version_id → app_versions.id` и `app_versions.app_id → apps.id`: разрешена через `CREATE TABLE apps` без FK на `current_version_id` в миграции `0003`, затем `CREATE TABLE app_versions` в `0004`, и в конце `0004` — `ALTER TABLE apps ADD CONSTRAINT ... FOREIGN KEY (current_version_id) REFERENCES app_versions(id)`.
- Роль пользователя — `TEXT + CHECK (role IN (...))`, не Postgres `ENUM` (проще расширять новой миграцией).
- Ограничения уникальности: `users.email`, `apps.slug`, `refresh_tokens.token_hash`, составной `UNIQUE (app_id, version_number)` на `app_versions`, составной `UNIQUE (user_id, app_id)` на `installs`.
- Индексы вручную (сверх тех, что уже создаёт `UNIQUE`): `refresh_tokens(user_id)`, `apps(author_id)`, `installs(app_id)`. Обоснование по каждому — в истории диалога, шаг 1. `installs(user_id)` и `app_versions(app_id)` отдельного индекса не требуют — уже покрыты как ведущая колонка соответствующих составных `UNIQUE`.
- `ON DELETE CASCADE` — только там, где дочерняя строка без родителя бессмысленна (`refresh_tokens.user_id`, `app_versions.app_id`). На `installs.*` каскада нет нигде — сознательно, чтобы нельзя было случайно снести историю покупок удалением приложения/пользователя.

Применено и проверено на обеих базах (`nest_apps`, `nest_apps_test`) через `npm run migrate` / `npm run migrate:test`, структура сверена вручную через `\d+` в `psql`.
